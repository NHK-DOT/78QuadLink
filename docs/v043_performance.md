# v0.4.3-dev 性能对照

## 这版改变了什么

v0.4.3-dev 新增独立 Go module `tools/simkit`，将优化功能整理成可选工具包：
JSON adapter/profile、每次运行的共享板初始化和清理、按需检查/录制/核验、
独立流式归档分析。Go1 仍是唯一经过实际验证的机器人 adapter。

控制热路径没有改变：v0.4.2 和 v0.4.3 的 motor-imu 都是原控制程序 ↔ 共享板 ↔
原控制器，IMU 从原传感器进入共享板。simkit 不参与每一帧的转发，不接管力矩计算。
因此本轮检验的是“工具化的额外开销”，不是语言重写或新的物理引擎性能。

## 对照方法

四种配置，正序与倒序各一轮；每组预热 10 s、采样 45 s；完整 full 场景，
同一固定站立动作，关闭 GUI/RViz，无观察探针。所有组使用同一构建的仿真 overlay。

- dds：合并控制器的 ROS/DDS 路径；不是最早十二独立控制器的基线。
- v042：v0.4.2 的共享电机 + IMU，以原 shell 包装器启动。
- v043：相同共享路径，以 Go simkit 启动。
- record：v043 加 Go 2 ms 周期采样、gzip BestSpeed 和 SHA-256 录制。

`record` 使用 simkit 的同一个 go1relay recorder 后端直接作为独立进程启动，
用于隔离采样/压缩/落盘成本；没有额外启动 `simkit record` 的第二个 CLI 父进程。
录制覆盖启动、预热、测量及收尾；记录总数不是恰好 45 秒的样本量。
录制结束后执行归档校验，校验不计入仿真测量窗口。

CPU 以一个逻辑核满载 100% 计，先按同一采样时刻累加各 PID 再求均值。
本轮明确计入 shell/simkit 启动包装进程和 recorder 后端，benchmark 自身与外部桌面
进程不计入；RSS 是进程合计而非去重 PSS。上下文切换统计只读进程主线程，故不
将其当作全体线程唤醒总量给出结论。尚未测量端到端控制延迟和最坏调度时间。

两轮短时静态站立数据不是长期压力测试或所有四足机器狗的性能保证。
既有实时倍率已经约为 1，CPU 降低不等于物理仿真速度等比例提高。

## 复现

```bash
./tools/simkit/compare_performance.sh
python3 tools/simkit/summarize_performance.py "$(cat artifacts/bench/latest-v043-matrix.txt)"
```

脚本保存每组原始 CSV、日志和元数据，另保存 Go 二进制和 adapter 的 SHA-256、
当前 tracked diff 与 simkit 源码副本，避免只用 `v0.4.3-dev` 名称标识实验。

## 实测结果

证据目录：`artifacts/bench/v043-matrix.BNNk1P/`，其中 `comparison.json` 包含
每组、每进程与归档详细数据。每种配置累计 90 个一秒采样点。

| 路径 | 第一轮 CPU | 第二轮 CPU | 平均 CPU | RSS 合计 MiB |
|---|---:|---:|---:|---:|
| 合并控制器 ROS/DDS | 57.47% | 64.91% | 61.19% | 570.65 |
| v0.4.2 共享电机 + IMU | 52.55% | 57.64% | 55.10% | 573.40 |
| v0.4.3 simkit，同一共享路径 | 49.11% | 50.18% | 49.64% | 572.82 |
| v0.4.3 + Go recorder 后端 | 44.84% | 52.24% | 48.54% | 580.93 |

八组 RTF 报告均为 1.0，站立切换、结束高度和 invalid_commands/stale_frames 检查通过。
共享路径没有改 C++ 控制算法或物理场景；这些是当前本机短时实测值，不是统计显著性证明。
运行期间未固定 CPU 亲和性，读取到 CPU governor 为 powersave；后台负载/动态频率及
仿真接触状态可能影响结果，未用隔离实验确定各自贡献。

**不能把 v0.4.3 相比 v0.4.2 的约 9.9% 观测差直接称为新增优化收益。**
两者的数据面没有改变，单组波动已达到多个 CPU 百分点。record 组总 CPU 反而更低，
同样不能说明压缩提高了物理仿真效率；本轮不声称已经精确测得净工具开销。

可直接定位到进程的额外成本：

- 两次 simkit 包装器在 45 s 测量窗口内 CPU 均为 0.00%，RSS 约 2.9 MiB；
  指 /proc 时钟 tick 分辨率下没有测得 CPU 增量，不是进程绝对不耗 CPU。
  原 shell 包装器也在测量窗口内 CPU 为 0.00%，占约 3.7 MiB。
- Go recorder 后端两轮分别 2.02%、2.27% CPU，RSS 8.33、8.30 MiB，
  说明按需录制确实增加了约 2.14 个 CPU 百分点的独立工作，不能只看整组差值。
- 两份归档分别 90833、89825 条，压缩体积减少 58.40%、58.50%；完整性核验通过，
  队列丢弃与无效帧计数均为零。采样前覆盖仍存在，不能称为全量无损状态录制。

本轮支持“v0.4.3 工具包装在等待期间很轻，录制开销小且可选”，不支持“换成 Go 包装
器就加速控制热路径”。此前 v0.4.2 的测量与本轮也不能直接拼成一条连续增益曲线。


## 十二路模式的当前同口径复测

用户进一步要求追溯最初十二路，因此在以上八组结束后又运行了“十二路 → 共享 → 十二路”
夹心对照。完整场景、固定站立、预热 10 s、每组采样 45 s，计入本次运行的辅助节点；
共享组额外计入 simkit 父进程。证据目录 `artifacts/bench/v043-legacy.hCW6uZ/`。

| 顺序 | 路径 | CPU 合计 | RSS 合计 MiB | 报告 RTF |
|---|---|---:|---:|---:|
| 1 | 保留的十二路 v0.1 controller | 127.11% | 594.93 | 1.0 |
| 2 | v0.4.3 共享电机 + IMU | 49.33% | 572.72 | 1.0 |
| 3 | 保留的十二路 v0.1 controller | 99.00% | 595.02 | 1.0 |

十二路两组均检查了所有十二个 controller active、站立切换和结束高度；共享组通过
原有 command/stale 检查，三组结束高度约 0.353–0.354 m。

相对前后两次十二路，CPU 分别低 **61.2%、50.2%**；以两次十二路均值 113.05% 为
参考则低 **56.4%**。RSS 合计少约 **22.25 MiB**。十二路前后自身波动很大，
所以更可靠的表述是“本场景约减半”，不能给出普遍固定的 56.4% 提升保证。
共享组的 49.33% 也与前面两次 v0.4.3 的 49.11%、50.18% 接近。

这是从十二路结构到当前聚合/共享/IMU路径的累计差异，不是 v0.4.3 工具包装本身带来
的加速。当前十二路保留的是 v0.1 UnitreeRealtimeController，并非更早的原版
UnitreeLeggedController；历史版本的取证和统计边界见
[四足仿真调研及历史基线](quadruped_optimization_landscape.md)。

